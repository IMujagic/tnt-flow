Proof, not claims.

Think and Type (tnt) runs your feature work through independent subagents: one writes failing tests, another makes them pass, others review, test the running system and audit. A step only counts when the tnt CLI has recorded real command output in a hash-chained ledger, bound to the exact code it ran against.

the concept

Agents do the work. The CLI decides whether it counted.

tnt has two layers that never swap roles. Subagents write tests, code, reviews and probes. A small deterministic Node CLI, with no dependencies, runs the commands, records what happened and decides every gate. No agent's description of its own work is ever read as evidence.

who does what

The agent layer

  • Skills such as /tnt:develop run in your session and spawn one fresh subagent per step.
  • Producers: test-author, implementer, planner, architect, scaffolder, codebase-analyst, claims-analyst.
  • Verifiers that can't edit code: code-reviewer, functional-tester, evidence-auditor.
  • Subagents can only dry-run a gate with tnt check. Only the orchestrator runs tnt gate.
whether it passed

The deterministic harness

  • Runs the configured test and style commands itself, so nobody can "prove" a step with true.
  • Hashes the working tree before and after each run. A command that changed the code is rejected as evidence.
  • Appends every run, approval, review and gate decision to a hash-chained ledger.
  • Decides each gate from that ledger and auto-commits at red, green and done.

tnt run F-7KQ2MX green
the core

The ledger is the proof. Try to fake it.

Each feature has its own ledger.jsonl. Every entry stores the hash of the entry before it (prev) and a sha256 of its own content (hash). Edit any entry and verification points at it. Re-hash it to cover up, and the next entry no longer links. This chain is computed live in your browser with the same rules the CLI uses.

Rewrite history

Evidence is bound to code, not to commits

treeHash()

Each run records a content hash of the working tree, computed through a temporary git index that honours .gitignore and leaves out .tnt/. Every gate after green must be proven on the green tree, so changing one line of code after green makes the later evidence stale.

seven gates

Each gate passes only on what the ledger shows

Gates run in this order. Passing one clears every later gate, so evidence is always rebuilt on top of the latest proven state. A failing gate prints the failing lines of each run it cites, so the next step starts from the failure instead of reading whole logs.

The flows, one board each

Each flow is a skill you start from Claude Code. Your session orchestrates, a fresh subagent does each step, and the CLI records and decides. Blue boxes wait for you.

guardrails

What the agents can't do

A PreToolUse guard hook checks every tool call a subagent makes. It works alongside the ledger: the hook stops the obvious shortcuts, and the hashes catch anything that gets past it.

Decide a gateSubagents can't run gate, approve, waive, unlock, sync, start or init, and can't import the harness modules directly.
Touch the evidenceOnly the CLI writes state.json, ledgers, logs, evidence/ and report.md. Direct writes are blocked.
Edit locked testsAfter red, the locked test files can't be edited, checked out, restored, stashed or reset. Changing them needs a recorded unlock with a reason.
Act in your nameapprove, waive, unlock and sync --relock open a permission prompt, even in auto mode. In claude -p they are refused.
Verify their own wayVerifiers are read-only, apart from their own draft files. Red, green and style always run the commands in .tnt/config.json.
Rewrite git historySubagents can't commit, merge, rebase, reset, stash, check out, restore, push or delete branches.

Where this stops. The guard hook reads commands as text, so a determined agent could hide a write from it, for example inside a decoded script. Treat it as one layer of defence, not a security boundary. Locked-test hashes and tree binding catch the result at the next gate, and tnt verify re-executes the evidence instead of trusting recorded results. The proof is report.md and tnt verify together, not either one alone.

any time

See where things stand

/tnt:status

Gates, attempts, waivers, unlocks and ledger integrity for every feature and review.

/tnt:verify F-…

Re-executes tests, style and functional evidence from scratch, then a fresh auditor judges it. Use it before a merge or a release.

tnt view --open

One self-contained HTML page: the ledger as a timeline, with logs, findings and the code diff between recorded trees.

tnt usage

Tokens per feature and per subagent, recorded by a SubagentStop hook. Statistics only, never evidence.

open source

Install it in two commands

Clone the repository, then from its root:

git clone https://github.com/IMujagic/tnt-flow.git && cd tnt-flow
claude plugin marketplace add .
claude plugin install tnt@think-and-type

Then, in any git repository: /tnt:onboard for an existing codebase or /tnt:new-project for a new one. Commands are /tnt:<skill> and agents are tnt:<agent>.

Requires a recent Claude Code, Node.js 18 or later, and git. The CLI has zero dependencies.
